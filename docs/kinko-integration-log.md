# 金庫アプリ連携の記録

別プロジェクト（`kinko-app-2f5e4`）の金庫・レジ現金点検の結果を、引継ぎ書に取り込むまでの経緯。
**仕様そのものは README の「🔐 金庫アプリとの連携」を見てください。** ここに残すのは
**なぜそうなっているか**、特に一度作って外したもの・作り直したものの理由です。

完了時点: `v1.11.1`（2026-09-17）／ 両アプリとも main にマージ済み

---

## 何ができるようになったか

```
引継ぎを投稿 → 「金庫アプリを開く」→ 点検 → ✕で戻る → 自動で引継ぎ書に取り込み → 印刷・保管
```

これまでLINEやメールで共有していた点検結果が、引継ぎ書の一部として残り、いつでも見返せて印刷もできます。

## 設計上の判断

### 連携方向は読み取り専用

こちらは金庫アプリのFirestoreを**閲覧専用アカウントで読むだけ**です。書き込みは一切しません。
Firebase JS SDK の複数アプリ初期化（`firebase.initializeApp(config, 'kinkoApp')`）を使っています。

不具合報告アプリと同じ方式です。連携先が増えても同じ形で足せます。

### 取り込んだ値は固定する

一度取り込んだ記録は、あとから金庫アプリ側が修正されても遡って書き換わりません。
**その時点の引継ぎ記録として残す**という扱いです。印刷して保管するものなので、後から中身が変わるほうが困ります。

### 店舗名は「対応付け」で解決する

両アプリで店舗名の付け方が違います（こちら `清川二丁目` ／ 金庫アプリ `福岡清川二丁目店`）。

どちらかに寄せると既存データに影響が出る（連絡ノートは店舗名で紐づいている）ため、
**オーナー設定で対応付けを登録する**方式にしました。接尾辞を機械的に削るような変換は、
金庫アプリ側に「清川事務所金庫」のようなこちらに対応しない項目があるため成立しません。

## 起きた問題と、その扱い

### 1. 実査が未入力のまま過不足が計算されていた

金庫アプリが「実査未入力」と「0円を数えた」を区別しておらず、数えないまま保存できました。
その記録は `実査合計 0円 ／ 過不足 -200,000円` という形になり、自動取り込みでそのまま
引継ぎ書に載り、印刷され、記録として残ります。

**こちらで一時的な防御を入れ（PR #24）、金庫アプリ側の根本対応後に外しました（PR #25）。**

外した理由が重要です。金庫アプリが「未入力では保存できない」ようになった以上、
保存された0円は**「数えた結果、金庫が空だった」**を意味します。弾き続けると、
**最も重大な事態こそ引継ぎ書に載らなくなります。**

テストは削除せず `kinko-empty-safe-test.js` として**逆向きに書き換えました**。
挙動を変えたなら、変えた先を固定しないと、将来また「0円は怪しいから弾こう」と
入れてしまっても誰も気づきません。

### 2. 別店舗の点検が保存されていた

金庫アプリが自分の最後に開いた店舗を覚えているため、こちらが博多住吉通りでも、
金庫アプリは清川二丁目を開いたまま保存されていました。

**エラーは出ず、取り込みも「成功」します。** こちらは博多住吉通り店の最新記録＝
数時間前のものを拾って引継ぎ書に載せました。誰も気づけません。

対応は3段階です。

| 段階 | 内容 | PR |
|---|---|---|
| 検出 | 点検店舗を必ず表示・引継ぎより古い記録は取り込まない | #26 |
| 案内 | 開く前に「どの店舗として開くか」を出す | #27 |
| 防止 | URLの `#store=` で開くべき店舗を渡す | #28 |

金庫アプリ側でも「〇〇店の点検として保存します」の確認が入りました。

**なお、店舗の取り違えは金庫アプリ単体のデータを壊す問題です。** 連携をやめても消えません。
次回の「前回の記録」も `*Delta` も、別店舗の値を土台にした誤りになります。
「連携を止めれば安全」ではなく「連携しているから気づける」という関係です。

### 3. 点検直後の記録を「古い」と誤判定した（こちらのバグ）

金庫アプリの `datetime` は**分までしか持ちません**（`18:56:50` に保存しても `"...T18:56"`）。
一方こちらの「開くを押した時刻」は秒まで持つため、`18:56:00 < 18:56:50` で古い判定になり、
**同じ分の中で保存された点検が必ず弾かれていました**（PR #29 で分単位の比較に修正）。

判定を入れるときは、**比較する両者の粒度を揃える**こと。

## 警告を増やしすぎない

この連携では、同じ事象に対して警告を出せる箇所が複数あります。ただし
**毎回出る警告は、本当に警告すべきときに読まれなくなります。**

実際、実査未入力の `-200,000円` が赤字で出続けていたことが問題の一部でした。

そのため PR #28 で、開く前の案内を**警告から事実の提示に戻しています**。

```
変更前： ⚠️ 金庫アプリで 博多住吉通り店 が選ばれているか確認してください（黄色の警告）
変更後： 金庫アプリは 博多住吉通り店 として開きます（通常の情報表示）
```

取り違えが ①URL指定 ②金庫アプリ側の保存前確認 の2段で防がれるようになったためです。
「違う店舗が出たら保存せず店長に連絡」は残しています。

## テストで3回踏んだこと

日時を固定文字列で書いたテストが、**実行した時間帯やタイムゾーン次第ですり抜けました**。

- 記録の日時が未来扱いになり、staleness の判定が効いていなかった
- 引継ぎの `createdAt` が過去になり、「最新の引継ぎ」が入れ替わっていた

いずれも**テストは通っているのに何も見ていない**状態です。
`tests/README.md` に注意として書きました。日時は `Date.now()` からの相対で作ってください。

**目視確認ではこの種のすり抜けを検出できません。** テストのassert化の優先度は、
この3回で上がりました（3層構造の改修に着手する前の前提条件）。

## 認識しておくこと

`kinkoConfig` には金庫アプリの**閲覧用パスワードが入っています**。Firestoreのルール上
「ログイン済みなら読める」ため、共通PINでログインしたスタッフの端末からは技術的に読み取れます
（画面には出ませんが、開発者ツールを使えば取り出せます）。

読み取り専用アカウントなので金庫アプリを壊される心配はありませんが、
**「PINを知っている人は金庫アプリの中身を見られる」**とは言えます。
不具合報告アプリの連携も同じ構造です。退職者が出たときにPINを変える理由が1つ増えます。
