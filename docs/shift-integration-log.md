# シフト管理アプリ連携の記録（進行中）

別プロジェクト（`shift-management-app-c6df2`）のヘルプ募集を、全画面共通のヘッダーに出すまでの経緯。
**仕様そのものは README の「🆘 シフト管理アプリとの連携」を見てください。** ここに残すのは
**なぜそうなっているか**と、**まだ決まっていないこと**です。

現在地: `v1.12.0`（2026-09-17）／ **こちら側の実装のみ完了。先方の実装と接続情報は未着。**

---

## なぜヘッダーなのか（連絡ノート案を取り下げた理由）

最初は「ヘルプ募集を連絡ノートに自動投稿して毎日リマインドする」案でした。取り下げています。

- ヘルプ募集は**流れる情報**です。連絡ノートは日々の投稿が積み上がる場所なので、募集が下に流れて埋もれます。埋まった募集も残り続けます
- **常に見えているものは、それ自体がリマインドです。** ヘッダーにすると「何時に通知するか」「何日繰り返すか」という設計判断がまるごと不要になり、募集が無くなれば黙って消えます

金庫アプリ連携で繰り返し確認した「**警告を増やしすぎると読まれなくなる**」と同じ方向の判断です。

## なぜ氏名を持たないのか

当初は「⚡ 中村さんの休み希望」のように誰の休みかを出す案もありました。運用側の判断で不要になりました。

> 応募を決めるのは**日時**であって、誰が休むかではない。誰が休んだかはシフト表で見られる。

この判断で、連鎖的に次が消えました。

- 「個人の休み希望を全店に見せてよいか」という運用判断そのもの
- **名簿との名寄せ**（この機能に限れば不要）
- 接続情報がPINログイン端末から読み取れることの実害（読めるのは「いつ・どこで人手が足りないか」だけ）

結果、この機能は**他の連携項目（出勤者表示・投稿者名の名簿選択）と切り離して単独で進められる**ようになりました。

## 「消えた＝確定」を受け取らなかった理由

先方の当初案は「確定したら `helpPostingsPublic` から削除する。消える瞬間を検知してほしい」でした。**受け取れないと回答しました。**

こちらは一覧を読むだけなので、ドキュメントが消えたとき、次の4つが同じに見えます。

1. 責任者が承認して確定した
2. 休み希望が取り下げられた
3. 日付が過ぎた
4. **読み取りに失敗した**（ルール設定ミス・権限エラー・通信断で空が返る）

1だけを「埋まりました」と知らせたいのに、2〜4も同じ通知になります。特に4が危険で、
**ルールの設定ミスで空が返ってきたら「全部埋まりました」と嘘を出します。**

これは金庫アプリで実際に踏んだ失敗と同じ形です。あちらでは「実査が未入力（値が無い）」を
「0円」として扱い、**過不足 -200,000円という嘘の数字**が出ました。
**「無い」を「意味のある値」として読むと必ず事故になる。**

そのため `status: "filled"` ＋ `filledAt` を48時間残してもらう形でお願いしています。
コード側も同じ方針で、読み取りに失敗したら `helpPostings` を空配列ではなく **`null` に倒し**、
バナーごと出しません（`renderHelpBanner` の先頭）。

## ドキュメントIDに店舗PINを入れないよう依頼した理由

先方の説明にこうありました。

> 店舗PIN(例 `fm71661`)でログインして最初に使われた店舗は、そのPIN文字列自体が `storeId` になります

ドキュメントIDが `<storeId>__<key>` 形式だと、該当する店舗では

- `helpPostingsPublic` を読める人が**シフト管理アプリの店舗PINを読める**
- `#help=fm71661__...` の形で**PINがURLに載る**
- こちらは全店の募集を全スタッフに見せるため、**他店のPINが画面に並ぶ**

先方は「氏名を含まないから安全」と判断していましたが、**IDそのものが認証情報になっているケース**が
抜けていました。氏名より影響が大きい可能性があります。ID をPINと無関係な値にするよう依頼済みです。

**この依頼が通っていなくても、こちらのコードは壊れません。** ただし対応付けを登録するまで
識別子がそのまま画面に出ます。オーナー設定に「名前が付いていない識別子」を表示しているのは、
それに気づけるようにするためです。

## 店舗の対応付けの向きが金庫アプリと逆な理由

- 金庫アプリ: こちらが**店舗名で問い合わせる** → `このアプリの店舗名 = 金庫アプリの店舗名`
- シフト管理アプリ: 募集が**識別子付きで届く** → `シフト管理アプリの識別子 = このアプリの店舗名`

同じ「店舗の対応付け」という名前でも向きが違います。設定画面の説明文とプレースホルダで示しています。

## 承認待ちを責任者だけに出す理由

「誰を採用するかは責任者の承認が必要」という運用のため、**応募が来たまま放置される**ことが起こります。
バナーの「⏳ 承認待ち N件」は `isAdminUser`（管理者メール登録者）のときだけ出します。
スタッフに出しても操作できることがありません。

ただし**個々の行の「⏳ 承認待ち」タグは全員に出します。** 既に応募があるかどうかは応募の判断材料になり、
これを隠すと応募済みの枠と空の枠が見分けられなくなるためです。

## まだ決まっていないこと

先方の実装と並行しているため、次は**届かない可能性を前提に**書いてあります（無ければその部分を出さないだけ）。

| 依頼中のもの | 無いとどうなるか |
|---|---|
| `startTime` / `endTime` | 区分名（`夕勤`）だけを表示。**他店のスタッフに時間が伝わらず、応募されません**（全店表示にした意味が薄れます） |
| `status: "filled"` / `filledAt` | 埋まったことを知らせられません（上記の理由） |
| ID からのPIN排除・`storeLabel` | 対応付けを登録するまで識別子がそのまま出ます |
| 1枠に必要な人数 | 2人必要な枠に1人応募した時点で「応募あり」に見えます |

接続情報（Firebase Config ＋ 閲覧専用アカウント）も未着です。未設定のあいだ、ヘッダーには何も出ません。
