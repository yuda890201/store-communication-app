**仕様そのものは README の「🆘 シフト管理アプリとの連携」を見てください。** ここに残すのは

B（出勤者）・C（投稿者名の名簿選択）・D（提出期間）は未着手。

## なぜヘッダーなのか（連絡ノート案を取り下げた理由）

最初は「ヘルプ募集を連絡ノートに自動投稿して毎日リマインドする」案でした。取り下げています。

- ヘルプ募集は**流れる情報**です。連絡ノートは日々の投稿が積み上がる場所なので、募集が下に流れて埋もれます。埋まった募集も残り続けます
- **常に見えているものは、それ自体がリマインドです。** ヘッダーにすると「何時に通知するか」「何日繰り返すか」という設計判断がまるごと不要になり、募集が無くなれば黙って消えます

金庫アプリ連携で繰り返し確認した「**警告を増やしすぎると読まれなくなる**」と同じ方向の判断です。

## なぜ氏名を持たないのか

当初は「⚡ 中村さんの休み希望」のように誰の休みかを出す案もありました。運用側の判断で不要になりました。

> 応募を決めるのは**日時**であって、誰が休むかではない。誰が休んだかはシフト表で見られる。

この判断で、連鎖的に次が消えました。

- 「個人の休み希望を全店に見せてよいか」という運用判断そのもの
- **名簿との名寄せ**（この機能に限れば不要）
- 接続情報がPINログイン端末から読み取れることの実害（読めるのは「いつ・どこで人手が足りないか」だけ）

結果、この機能は**他の連携項目（出勤者表示・投稿者名の名簿選択）と切り離して単独で進められる**ようになりました。

## 「消えた＝確定」を受け取らなかった理由

先方の当初案は「確定したら `helpPostingsPublic` から削除する。消える瞬間を検知してほしい」でした。**受け取れないと回答しました。**

こちらは一覧を読むだけなので、ドキュメントが消えたとき、次の4つが同じに見えます。

1. 責任者が承認して確定した
2. 休み希望が取り下げられた
3. 日付が過ぎた
4. **読み取りに失敗した**（ルール設定ミス・権限エラー・通信断で空が返る）

1だけを「埋まりました」と知らせたいのに、2〜4も同じ通知になります。特に4が危険で、
**ルールの設定ミスで空が返ってきたら「全部埋まりました」と嘘を出します。**

これは金庫アプリで実際に踏んだ失敗と同じ形です。あちらでは「実査が未入力（値が無い）」を
「0円」として扱い、**過不足 -200,000円という嘘の数字**が出ました。
**「無い」を「意味のある値」として読むと必ず事故になる。**

そのため `status: "filled"` ＋ `filledAt` を48時間残してもらう形でお願いしています。
コード側も同じ方針で、読み取りに失敗したら `helpPostings` を空配列ではなく **`null` に倒し**、
バナーごと出しません（`renderHelpBanner` の先頭）。

## 指摘が通った結果（先方の最終仕様）

依頼した5点はすべて反映されました。

| 依頼 | 結果 |
|---|---|
| `status: "filled"` ＋ `filledAt` を残す | ✅ 入った。48時間ほどで削除 |
| ドキュメントIDからPINを外す | ✅ Firestore自動採番になった |
| `storeKey` をPINと無関係の値にする | ✅ 店舗ごとに固定のUUID |
| `storeLabel`（人が読める名前） | ✅ 入った。未設定のあいだは `(表示名未設定)` |
| `startTime` / `endTime` | ✅ 入った |
| 1枠に必要な人数 | 常に1人と確定（枠は内部で分解済み）。`requiredCount` 不要 |

**指摘2（IDにPINを入れない）が、先方の権限設計の穴も塞ぎました。** 先方の説明によれば、従来のルールは「スポットワーカーとして登録されていないログイン済みアカウント」を自動的にスタッフ扱いにする作りで、そのまま閲覧専用アカウントを発行していたら、**こちらに渡す認証情報で店舗の全データ（時給・スタッフ名簿・立候補者の氏名）が読めてしまう**ところだったとのことです。`externalReaders` という権限区分が新設され、`helpPostingsPublic` の読み取りだけに絞られました。

指摘したのは「IDに認証情報が混ざっているのでは」という一点で、権限設計の話はしていません。**一つ具体的に疑ったことが、見えていなかった別の穴に当たった**という形です。

## 先方の仕様に合わせて足した2つの防御

**1. `(表示名未設定)` を店舗名として扱わない**

オーナーが表示名を設定するまで、`storeLabel` にはこの文字列が入ります。空文字ではないため、素直に書くと

- 画面に `(表示名未設定)` が店舗名として出る
- 「名前が付いていない識別子」の一覧にも挙がらない（`storeLabel` が空ではないため）

つまり**気づく手段ごと無くなります**。合図として扱い、画面には `⚠️ 店舗名未設定` と出し、オーナー設定にも挙げるようにしました。`storeKey` はUUIDなので、代わりに出しても意味がありません。

**2. `filled` なのに `filledAt` が無いものは出さない**

先方の削除処理は「その店舗がシフト管理アプリを開いたとき」に走ります。**48時間ちょうどでは消えず、店舗がしばらく開かなければ `filled` のまま残り続けます。** 表示を止めるのはこちらの責任で、判断材料は `filledAt` だけです。これが欠けていると、いつ埋まったのか分からないまま「✅ 埋まりました」が戻らなくなります。分からないものは出しません。

## 「取り下げ」を「埋まりました」と言わずに済んでいる理由

先方の仕様では、休み希望が取り下げられた募集は **`filled` を経由せず即削除**されます。先方からも「この消え方を『埋まりました』と通知しないように」と注意がありました。

こちらは**消失を検知していません**（その時点で読める一覧をそのまま出すだけ）。そのため取り下げられた募集は黙って一覧から消え、通知は出ません。「消えた」を意味のある出来事として読まない、という最初の判断がそのまま効いています。

## ドキュメントIDに店舗PINを入れないよう依頼した理由

先方の説明にこうありました。

> 店舗PIN(例 `fm71661`)でログインして最初に使われた店舗は、そのPIN文字列自体が `storeId` になります

ドキュメントIDが `<storeId>__<key>` 形式だと、該当する店舗では

- `helpPostingsPublic` を読める人が**シフト管理アプリの店舗PINを読める**
- `#help=fm71661__...` の形で**PINがURLに載る**
- こちらは全店の募集を全スタッフに見せるため、**他店のPINが画面に並ぶ**

先方は「氏名を含まないから安全」と判断していましたが、**IDそのものが認証情報になっているケース**が
抜けていました。氏名より影響が大きい可能性があります。ID をPINと無関係な値にするよう依頼済みです。

**この依頼が通っていなくても、こちらのコードは壊れません。** ただし対応付けを登録するまで
識別子がそのまま画面に出ます。オーナー設定に「名前が付いていない識別子」を表示しているのは、
それに気づけるようにするためです。

## 店舗の対応付けの向きが金庫アプリと逆な理由

- 金庫アプリ: こちらが**店舗名で問い合わせる** → `このアプリの店舗名 = 金庫アプリの店舗名`
- シフト管理アプリ: 募集が**識別子付きで届く** → `シフト管理アプリの識別子 = このアプリの店舗名`

同じ「店舗の対応付け」という名前でも向きが違います。設定画面の説明文とプレースホルダで示しています。

## 承認待ちを責任者だけに出す理由

「誰を採用するかは責任者の承認が必要」という運用のため、**応募が来たまま放置される**ことが起こります。
バナーの「⏳ 承認待ち N件」は `isAdminUser`（管理者メール登録者）のときだけ出します。
スタッフに出しても操作できることがありません。

ただし**個々の行の「⏳ 承認待ち」タグは全員に出します。** 既に応募があるかどうかは応募の判断材料になり、
これを隠すと応募済みの枠と空の枠が見分けられなくなるためです。

## 「ヘッダーに何も出ない」を追えるようにした経緯

接続設定を入れたのにヘッダーが空、という状態が起きた。調べると**接続も読み取りも成功しており**、
届いた募集がすべて過去日で除外されていただけだった。ただしそう判断するにはコードを読む必要があった。

ヘッダーは「募集が無い」ときも「連携が壊れている」ときも何も出さない。これはスタッフの画面に
意味のない情報を増やさないための設計なので変えず、代わりに🔒オーナー設定へ内訳を出した（`v1.14.0`）。

```
✅ 接続できています。届いている募集 5件 ／ ヘッダーに表示中 4件
（除外: 過去日 1件）
```

**この表示が、次の切り分けをそのまま可能にした。**

## 過去日ばかりだった本当の原因（シフト管理アプリ側）

上の表示で「接続は成功・全件過去日」までは掴めたが、なぜ過去日ばかりなのかは分からなかった。
先方に「今日以降の日付で休み希望を1件入れてほしい」と依頼したところ、**その操作自体ができない状態**
だったことが判明した。

- 休み実績入力の「表示基準日（本日）」が、HTMLに `2026-08-01` と直書きされたまま、
  プログラム側から今日に直していなかった
- そのためログインするたび**過去の日付から30日分**が並び、休み希望を入れると必ず過去日の募集になっていた
- あわせて、スタッフ選択欄が `onchange` のたびに選択肢を作り直しており、**先頭の1人以外を選べなかった**

どちらも先方が修正・デプロイ済み。**こちら側の実装に原因は無かった。**

この一件は、**「何も出さない」設計には必ず「なぜ出ないのかを追える場所」が要る**ことを示している。
ヘッダーを黙らせたままにしたのは正しかったが、オーナー設定の内訳が無ければ、
こちらの不具合を疑って時間を使っていた。

## 次の段階（未着手）

B（出勤者の引継ぎ書表示）・C（投稿者名の名簿選択）は、どちらも**スタッフ個人を識別できること**が前提になる。
先方に確認したところ、名簿の `id` は `(人数 + 1)` で振られる連番で、**店舗をまたいで重複し、
削除で番号が変わる**ため識別子には使えないことが分かった。シフトの割り当ては現在**氏名の文字列**で
突き合わせており、同姓同名は先方でも区別できていない。

そのため「店舗をまたいで一意で消えないスタッフIDを新設する」ところからになる。
**シフト管理アプリが発行する案（案A）で合意方向。** 名簿の実体がそちらにあるため。

### `staffId` があっても解決しないこと

**こちらは「その人が本人であること」を確かめられない。** 全スタッフが同じ共通PINアカウントで
ログインするため、名簿を受け取ってもできるのは「一覧から自分を選んでもらう」ことだけで、
他人を選ぶことも技術的には可能。

それでも導入する価値はある。**いま起きているのは「なりすまし」ではなく「取り違え」**だから。

- 共有端末で前の人の名前が残ったまま投稿され、別人の名前で引継ぎが記録される
- 名前が未入力の端末では投稿者が「スタッフ」とだけ出る（実際にそうなっていた）

自由入力から名簿選択に変わるだけで、この2つは消える。連絡ノートの「未読④ケン」も同じ性質で、
**名簿から選んだ本人申告に基づく**ものになる。本人性まで要るならスタッフ個人にアカウントを配る話になり、
両アプリとも作りが変わるため別議題。

### 名簿に氏名が入ることについて

`helpPostingsPublic` は氏名を含まない設計にしてもらったが、名簿はそうはいかない。接続情報は
共通PINでログインした端末から技術的に読み取れる。

ただし**新しい露出にはならない。** このアプリは引継ぎ・連絡ノート・掲示板の投稿者名をすでに
全スタッフに表示しており、同じ顔ぶれの名前が既に見えている。

### B は C と分ける

Bに必要なのは「その日その店舗に誰が入るか」＝**シフト表そのもの**で、名簿より踏み込んだ情報になる
（誰がいつ働くかが全部読める）。名簿ミラーとは別コレクションにし、**当日と翌日ぶんだけ**に絞る形を提案済み。

### D（提出期間のリマインド）

先方に「提出期間・締切」の概念自体が無く、新規設計が必要。半月ごとの具体的な区切りは技術ではなく
運用ルールのため、**店主への確認が要る。**

## 店舗名が「付いている」のに自店と見なせなかった (2026-09-19)

先方が未来日の募集を4件登録し、ヘッダーに出た。`storeLabel` も `(表示名未設定)` ではなく
**`福岡清川二丁目店`** が入っていた。名前は付いている。それでも **`📍 自店` の印が出なかった。**

こちらの判定は `storeLabel === activeStore` の文字列一致で、このアプリ側の店舗名は
**`清川二丁目`**。同じ店舗なのに文字列が違うため、自店と見なせない。

### 直した箇所は判定ではなく表示

文字列を寄せる（部分一致・正規化）ことは考えたが採らなかった。`福岡清川二丁目店` と
`清川二丁目店` が別店舗である可能性を、こちらは否定できない。**推測で同一視すると、
他店の募集に「自店」と出る**ほうが害が大きい。対応付けの登録で解決する。

問題だったのは**対応付けを登録できなかったこと**のほうだった。オーナー設定には
「店舗名が分からない識別子」しか出しておらず、`storeLabel` が入っている店舗は一覧から消える。
結果、画面に出ていたのはUUIDだけで、**どのUUIDがどの店舗なのか分からず、対応付けの行を書けない。**

届いている識別子とこちらでの表示を**対にして**出すよう変えた。

```
届いている店舗:
3f2a9c1e-… → 福岡清川二丁目店　← このアプリの店舗名（清川二丁目 など）と違います。自店ならば対応付けの登録が要ります
7b41d0aa-… → 清川二丁目　（対応付け済み）
```

**「名前が付いていない」だけを異常として扱っていたのが狭かった。** 実際に起きたのは
「名前は付いているが、こちらの名前と違う」で、これは前の表示では検知できないどころか、
正常として一覧から消えていた。

## `postedToShareful` の追加 (2026-09-19)

先方から追加のみのスキーマ変更の連絡。シェアフル（外部の求人サービス）に出した枠かどうかを
責任者が記録できるようにしたもの。先方とシェアフルの連携は一方通行で、シェアフル側で人が
決まってもシフト管理アプリには伝わらないため、連携ツールが同じ枠を毎朝取り込んで**二重に
求人を出してしまう**問題への対処とのこと。

こちらは対応不要だったが、`📣 外部募集中` の印として出すことにした。スタッフから見た意味は
「外部にも出ているので、入るなら早めに」。

**`true` でも `status` は `open` のまま**で、「もう埋まった」という意味ではない。
社内スタッフの立候補は引き続き受け付ける。ここを取り違えると立候補できるはずの枠が
埋まったように見えるため、テストで固定した（募集件数に数える／`埋まりました` と出さない／
タップで応募先が開く）。
